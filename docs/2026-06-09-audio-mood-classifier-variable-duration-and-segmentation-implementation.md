## 1. Overview

This document records the two architectural updates made to the data generation layer on 2026-06-09:

1. **`generate_songs_sagmens.py` was created** as a new parallel pipeline step that extracts the same three audio windows used for spectrograms and exports each as a raw MP3 file. This provides a paired raw-audio dataset that can be fed directly to waveform-based models such as MERT, while the spectrogram pipeline continues serving the EfficientNet image classifier.

2. **Both scripts were refactored** to replace the single hardcoded `SEGMENT_SECS = 30` duration with a two-constant system: `SEGMENT_SECS` (fixed 30-second boundary guard) and `SEGMENT_DURATION_SECS` (configurable window width). This makes the extraction window independently adjustable — 30 s, 10 s, 5 s, or any other value — without touching any parsing, verification, or offset formula logic.

        │                                     │

Both branches read the same catalog file and apply identical offset math, so the three audio windows extracted per track are **bit-for-bit time-aligned** across both pipelines. A PNG and its corresponding MP3 always represent the exact same portion of the source recording.

## 3. `generate_songs_sagmens.py` — Role, Inputs, and Outputs

### 3.1 Role

`generate_songs_sagmens.py` is Pipeline Step 2b. It consumes `docs/catalog_with_paths.md`, validates every track entry interactively, loads three short audio windows per track via `librosa`, applies EBU R128 loudness normalization, and writes each window to disk as an MP3 file. It does not generate any images and does not modify any source audio files.

### 3.2 Inputs

| Input | Location | Format |
|---|---|---|
| Matched track catalog | `docs/catalog_with_paths.md` | Markdown (generated by `prepare_dataset.py`) |
| Source audio files | Network path / local drive (UNC or absolute) | `.m4a`, `.mp3`, `.flac`, or any format supported by librosa |

### 3.3 Outputs

For each validated track in the catalog, three MP3 files are written:

```
data/mp3/<category>/<Sanitized_Track_Name>_seg1.mp3   ← segment 1 (near start)
data/mp3/<category>/<Sanitized_Track_Name>_seg2.mp3   ← segment 2 (midpoint)
data/mp3/<category>/<Sanitized_Track_Name>_seg3.mp3   ← segment 3 (near end)
```

The three mood category subdirectories are created automatically if absent:

```
data/mp3/
├── calm_melancholic/
├── moderate_neutral/
└── energetic_upbeat/
```

### 3.4 What the Script Does NOT Do

- It does not copy, move, or modify source audio files.
- It does not generate spectrograms or any image files.
- It does not start processing until the user explicitly presses `[1]` in the verification menu.

## 5. Variable Duration Architecture

### 5.1 The Problem with a Single Constant

The original design used `SEGMENT_SECS = 30` for three distinct purposes simultaneously:

1. The width of each extracted audio window (what gets loaded).
2. The boundary guard skipped at the start of the track.
3. The boundary guard skipped at the end of the track.

Tying these three roles to one value made it impossible to change the window width without inadvertently changing the boundary guards, and vice versa.

### 5.2 The Two-Constant Solution

The refactor splits the single constant into two independent values:

```python
SEGMENT_SECS          = 30      # boundary guard — always 30 s, never changes
SEGMENT_DURATION_SECS = 10.0   # window width  — freely adjustable
```

**`SEGMENT_SECS` (boundary buffer):** A fixed 30-second exclusion zone at both ends of every track. The first 30 seconds are skipped to avoid intros, fade-ins, and spoken introductions. The last 30 seconds are skipped symmetrically to avoid outros, fade-outs, and applause. This constant is intentionally not adjustable without careful consideration of how it affects the minimum track length threshold.

**`SEGMENT_DURATION_SECS` (window width):** The only value that needs to change when adjusting segment length. Changing it from `10.0` to `5.0`, `30.0`, or any other value automatically recalculates the threshold, the midpoint window centring, and the zero-padding target — no other lines of code require editing.

### 5.3 Affected Lines When Changing `SEGMENT_DURATION_SECS`

The following expressions read `SEGMENT_DURATION_SECS` and update automatically:

| Expression | Location | Effect |
|---|---|---|
| `seg = float(SEGMENT_DURATION_SECS)` | `segment_offsets()` | Window width used in all three offset formulas |
| `threshold = 2.0 * buffer + 3.0 * seg` | `segment_offsets()` | Minimum track length required for standard case |
| `seg_samples = int(SEGMENT_DURATION_SECS * SAMPLE_RATE)` | `process_catalog()` | Zero-pad target in samples |
| `duration=float(SEGMENT_DURATION_SECS)` | `librosa.load(...)` | Seconds of audio decoded per window |

### 5.4 Supported Configurations

| `SEGMENT_DURATION_SECS` | Threshold | Use case |
|---|---|---|
| `5.0` s | `2×30 + 3×5 = 75 s` | High-density CNN input; tight spectral frames |
| `10.0` s | `2×30 + 3×10 = 90 s` | **Current setting** — near-1:1 time-to-pixel mapping |
| `15.0` s | `2×30 + 3×15 = 105 s` | Medium density; good for moderate-tempo analysis |
| `30.0` s | `2×30 + 3×30 = 150 s` | Legacy full-window; broadest temporal context |

## 6. Segment Offset Math — Dynamic Threshold

### 6.1 Variables

```python
seg    = float(SEGMENT_DURATION_SECS)   # window width
buffer = float(SEGMENT_SECS)            # 30.0 — fixed guard
threshold = 2.0 * buffer + 3.0 * seg   # minimum track length for standard case
```

### 6.2 Standard Case (total ≥ threshold)

| Segment | Start offset | Window |
|---|---|---|
| 1 — Near start | `buffer` | `[30 s → 30+seg s]` |
| 2 — Midpoint | `total/2 − seg/2` | `[mid−seg/2 → mid+seg/2]` |
| 3 — Near end | `total − buffer − seg` | `[total−30−seg → total−30]` |

**Derivation of the threshold:** The binding constraint is that Segment 2 must not overlap Segment 3:

```
Seg 2 end ≤ Seg 3 start
total/2 + seg/2 ≤ total − buffer − seg
buffer + 3/2 × seg ≤ total/2
total ≥ 2 × buffer + 3 × seg
```

Because the threshold is computed at runtime from the two constants, it automatically adjusts whenever either constant is changed.

### 6.3 Example — 240-Second Track at Current Settings (`seg = 10`, `buffer = 30`)

```
threshold = 2×30 + 3×10 = 90 s   →   240 ≥ 90, standard case applies

Segment 1:  offset  30 s     window [30 s  →  40 s]
Segment 2:  offset 115 s     window [115 s → 125 s]
Segment 3:  offset 200 s     window [200 s → 210 s]

Untouched zones:  [0 → 30 s]  and  [210 → 240 s]  (30 s buffer at each end)
Gap between segments:  75 s on each side of Segment 2
```

```
0    30  40              115 125              200 210    240
│guard│S1│     75 s      │S2 │     75 s       │S3 │guard│
```

### 6.4 Short-Track Fallback (total < threshold)

```python
third = total_secs / 3.0
return {1: 0.0, 2: third, 3: third * 2.0}
```

The boundary guards are not applied for tracks below the threshold. The available duration is divided into three equal thirds starting from 0. All offsets are guaranteed to be within `[0, total_secs)`, and any segment that runs past the end of the file is zero-padded to `seg_samples` in `process_catalog`.

## 7. EBU R128 Loudness Normalization in the MP3 Pipeline

### 7.1 Why Normalization Is Required for MERT

MERT (Music Understanding Model with Large-Scale Self-Supervised Training) was pre-trained on audio at a consistent loudness level. Its convolutional front-end learns relative spectral and temporal patterns, not absolute amplitude. Without normalization, a quietly mastered 1970s recording and a loudly mastered modern track would present very different signal energies to the model for reasons unrelated to mood, introducing spurious variance into fine-tuning.

`generate_spectrograms.py` uses peak normalization (sufficient for visual spectrogram consistency). `generate_songs_sagmens.py` uses the more rigorous EBU R128 integrated loudness standard, which better matches MERT's pre-training conditions.

### 7.2 Implementation

```python
meter = pyln.Meter(sr)   # BS.1770 meter at the segment's actual sample rate
loudness = meter.integrated_loudness(y.astype(np.float64))
y = pyln.normalize.loudness(
    y.astype(np.float64), loudness, TARGET_LUFS
).astype(np.float32)
```

`pyln.Meter` implements the ITU-R BS.1770 / EBU R128 gating algorithm. It computes the integrated loudness of the segment in LUFS (Loudness Units Full Scale). `pyln.normalize.loudness` then applies the gain required to reach `TARGET_LUFS = -20.0`, which is a standard broadcast pre-processing target.

The array is temporarily cast to `float64` for the meter computation (as required by pyloudnorm) and immediately cast back to `float32` for downstream processing.

### 7.3 Silent Segment Guard

```python
try:
    meter = pyln.Meter(sr)
    loudness = meter.integrated_loudness(y.astype(np.float64))
    y = pyln.normalize.loudness(...).astype(np.float32)
except Exception:
    pass   # silent or unmeasurable segment — write as-is
```

The BS.1770 algorithm cannot compute a valid LUFS value for a segment that is entirely silent or too short to measure. pyloudnorm raises an exception in these cases rather than returning an invalid number. The `try/except` guard catches this and leaves the segment unchanged.

### 7.4 Safety Clip After Normalization

```python
y = np.clip(y, -1.0, 1.0)
```

Normalization boosts can push a transient sample above ±1.0 if the original segment had a very brief peak significantly louder than its average loudness. The clip caps the waveform to the float32 legal range before the `* 32767` scaling in `save_segment_mp3`, preventing hard digital clipping artifacts in the output file.

## 8. Temporal Density and the 400 × 400 Canvas

This section explains the perceptual and computational consequences of choosing different values of `SEGMENT_DURATION_SECS` for spectrogram generation.

### 8.1 How Spectrograms Are Rendered

`generate_spectrograms.py` renders every segment as a 400 × 400 pixel image using these fixed parameters:

```python
S = librosa.feature.melspectrogram(y=y, sr=sr, n_mels=128, hop_length=512)
# axes: 128 frequency bins (vertical) × N_frames time frames (horizontal)
# rendered onto IMAGE_SIZE=(4,4) inches at dpi=100 → 400×400 px
```

The number of time frames produced is:

```
N_frames ≈ ceil(SEGMENT_DURATION_SECS × SAMPLE_RATE / HOP_LENGTH)
         = ceil(SEGMENT_DURATION_SECS × 22050 / 512)
```

The image is always 400 pixels wide regardless of `N_frames`, because `aspect="auto"` stretches (or compresses) the time axis to fill the canvas.

### 8.2 Temporal Density at Different Window Widths

| `SEGMENT_DURATION_SECS` | Samples decoded | Time frames (N_frames) | Pixels per frame | Frame per pixel |
|---|---|---|---|---|
| `5.0 s` | 110 250 | ≈ 216 | **1.85 px / frame** | 0.54 |
| `10.0 s` | 220 500 | ≈ 431 | **0.93 px / frame** | 1.08 |
| `15.0 s` | 330 750 | ≈ 646 | **0.62 px / frame** | 1.62 |
| `30.0 s` | 661 500 | ≈ 1292 | **0.31 px / frame** | 3.23 |

**Pixels per frame > 1.0 means the image is up-sampled** — each STFT hop window expands across more than one horizontal pixel. Every individual frequency snapshot in time is rendered as a visually distinct vertical stripe.

**Pixels per frame < 1.0 means the image is down-sampled** — multiple STFT hop windows are compressed into a single pixel column. matplotlib's nearest-neighbour interpolation (`interpolation="nearest"`) means only one frame per column survives; fine temporal events between sampled frames are discarded.

### 8.3 The 5-Second Configuration — High-Density Patterns

At `SEGMENT_DURATION_SECS = 5.0`, 216 time frames are stretched onto 400 horizontal pixels (ratio ≈ 1.85). Each 23-millisecond hop window occupies approximately two canvas columns.

**Practical consequences for the CNN backbone:**

- **Sharp transient boundaries:** A drum hit, chord attack, or vocal onset spans roughly 2–4 hop windows (~46–92 ms). At 5 s, these events occupy 4–8 horizontal pixels, making them clearly visible as distinct vertical transitions. At 30 s the same event compresses to ≤ 1 pixel and may disappear entirely.
- **Frequency structures are unchanged:** The vertical axis always has 128 Mel bins regardless of window duration. Harmonic patterns, chord voicings, and vowel formants appear at the same vertical scale regardless of `SEGMENT_DURATION_SECS`.
- **Denser training signal per pixel:** The CNN receives more information per pixel column, since each column represents a unique hop window rather than an average of several compressed frames.
- **Trade-off — shorter temporal context:** 5 seconds captures roughly one phrase or two bars of music at typical tempos. For mood classification tasks that benefit from longer musical context (e.g., distinguishing a long ambient swell from a short energetic burst), a 10- or 30-second window provides more temporal range per image.

### 8.4 The 10-Second Configuration — Near 1:1 Mapping (Current Setting)

At `SEGMENT_DURATION_SECS = 10.0`, 431 frames map onto 400 pixels (ratio ≈ 0.93). This is the closest the pipeline gets to a one-to-one mapping between STFT frames and image columns — approximately one hop window per pixel, with minimal compression. It balances temporal resolution against musical context and is the current production setting in both scripts.

### 8.5 Choosing a Configuration

| Goal | Recommended `SEGMENT_DURATION_SECS` |
|---|---|
| Maximum temporal sharpness for transient-rich genres (e.g., EDM, rock) | `5.0` |
| Balanced resolution and musical context | `10.0` (current) |
| Broader phrase-level context for ambient / classical genres | `15.0`–`30.0` |
| Matching original 30-second spectrogram convention | `30.0` |

## 11. Deterministic Alignment Between Pipelines

The following five values are identical in both scripts and constitute the complete formal specification of the time windows extracted per track:

| Parameter | Value | Determines |
|---|---|---|
| `SAMPLE_RATE` | `22050` Hz | Resampling resolution for `librosa.load` |
| `SEGMENT_SECS` | `30` s | Buffer guard applied at both ends of every track |
| `SEGMENT_DURATION_SECS` | `10.0` s | Width of every extracted window |
| `offset` | `segment_offsets(total_secs)[idx]` | Identical float, same arithmetic in both files |
| `duration` | `float(SEGMENT_DURATION_SECS)` | Passed directly to `librosa.load` in both files |

Because `total_secs` is read from the file's metadata tags by `mutagen.File(audio_path).info.length` — a deterministic read of an immutable field — both scripts always receive exactly the same float and compute exactly the same three offsets. The resulting waveform array `y` represents an identical time window in both cases. The only divergence after that point is what each script does with `y`: spectrograms apply peak normalization and render a PNG; the MP3 pipeline applies LUFS normalization and encodes an MP3.
